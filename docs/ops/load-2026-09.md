# Нагрузочный прогон, сентябрь 2026

Спецификация: `docs/superpowers/specs/2026-09-17-worker-queue-ops-design.md`, раздел 10.
Скрипт: `scripts/load/run.ts` (`npm run load`), мок модели: `scripts/load/mock-provider.ts` (`npm run load:mock`).

| Сценарий | `--scenario` | Цель |
|---|---|---|
| 300 одновременных сессий открывают библиотеку и страницу симуляции | `pages` | p95 < 500 мс |
| 300 входов за минуту с одного IP, 10 % с ошибкой | `logins` | ни одного 429 для верных |
| 20 генераций одновременно при двух воркерах по 2 слота | `generations` | все завершаются; позиции честные; p95 страниц не хуже прогона без генераций более чем вдвое |
| `kill -9` воркера посреди генерации | `kill-worker` | задание перезапущено и завершено вторым воркером |
| Рестарт веба посреди генерации | `restart-web` | SSE переподключается, прогресс не теряется |

Что меряет скрипт:

- `pages`: 30 пользователей `load-N@example.test`, у каждого 10 входов, итого 300 сессий. Все сессии разом, в каждом раунде, открывают `/library`, `/api/simulations`, `/api/simulations/<id>` и `/?id=<id>`. p95 считается по всем запросам, сбоку показан разрез по адресам. Подготовка (регистрация, раскладка примеров, входы) в замер не входит.
- `logins`: 300 входов с шагом 200 мс, у всех один `X-Forwarded-For` (`--ip`). Каждый десятый вход — с неверным паролем. Неверные распределены по разным аккаунтам, по одному на человека, иначе счётчик идентификатора сам закрыл бы аккаунт.
- `generations`: p95 страниц по тем же 300 сессиям сначала без генераций, потом через 5 секунд после постановки 20 генераций (режим «Быстро»). Скрипт следит за каждым заданием по SSE, как мастерская. «Позиции честные» значит, что номер в очереди у каждого задания только уменьшался.
- `kill-worker` и `restart-web`: одна генерация. Когда в журнале появляется `plan-ready` (задание уже у воркера), выполняется `--kill-cmd` или `--restart-cmd`. При обрыве скрипт переподключается и читает журнал заново. Если после переподключения журнал короче, чем был, прогон падает.

## Локальный прогон на ноутбуке разработчика, не на копии сервера

17 сентября 2026, 07:41–07:53 по местному времени (в заголовках разделов ниже время UTC).
Это проверка скрипта и поведения системы, **а не приёмочный замер**: цифры страниц зависят от машины, а генератор нагрузки работал на той же машине, что и сервер.

### Стенд

- MacBook Pro, Apple M1 Pro (10 ядер), 16 ГБ, macOS 26.6; Node 26.8; Postgres 16.14 в контейнере `showmehow-pg`, отдельная база `tesseract_load` (создана, `npm run migrate` 001–005, после прогона удалена).
- Код: ветка `worker-queue-ops` на `c9c50fe` плюс `scripts/load`; сборка `npm run build`.
- Веб: `next start -p 3500` (производственная сборка), `SHOWMEHOW_TRUST_PROXY=1`, `SHOWMEHOW_EMBEDDED_WORKER=0`.
- Два воркера `npm run worker`, `WORKER_CONCURRENCY=2`.
- Мок модели `npm run load:mock` на порту 3599 (`MOCK_PORT=3599`), генератор отвечает через 20 с (`MOCK_GENERATOR_DELAY_MS` по умолчанию). Провайдер задан окружением: `SHOWMEHOW_API_KEY=test`, `SHOWMEHOW_MODEL=mock-gen`, `SHOWMEHOW_VISION_MODEL=mock-vision`, `SHOWMEHOW_BASE_URL=http://localhost:3599/v1`.
- `SHOWMEHOW_DATA_DIR` — временный каталог вне репозитория, общий для веба и воркеров.

Команды (`B=http://127.0.0.1:3500`):

```bash
npm run load -- --base $B --scenario pages
npm run load -- --base $B --scenario pages --sessions 100
npm run load -- --base $B --scenario logins
npm run load -- --base $B --scenario generations
npm run load -- --base $B --scenario kill-worker --kill-cmd kill-worker.sh
# вместо убитого воркера запущен третий, дальше снова два воркера
npm run load -- --base $B --scenario restart-web --restart-cmd restart-web.sh            # SIGTERM
npm run load -- --base $B --scenario restart-web --restart-cmd "SIGNAL=KILL restart-web.sh"  # SIGKILL
```

`kill-worker.sh` убивает именно тот воркер, который держит задание:

```bash
pid=$(docker exec showmehow-pg psql -U showmehow -d tesseract_load -tAc \
  "SELECT split_part(locked_by, ':', 2) FROM jobs WHERE status = 'running' LIMIT 1")
kill -9 $pid
```

`restart-web.sh` посылает вебу сигнал (`kill -$SIGNAL`, по умолчанию TERM), ждёт, пока освободится порт, и запускает `next start` заново.

### Итог

| Сценарий | Что прогнано | Цель |
|---|---|---|
| `pages` | 300 сессий × 3 раунда, 3600 запросов, 0 ошибок, p95 **713 мс** (повтор: 763 мс) | **не достигнута** |
| `pages`, уменьшенный | 100 сессий × 3 раунда, 1200 запросов, 0 ошибок, p95 **293 мс** | достигнута |
| `logins` | 300 входов за 61 с, один IP; 30 неверных получили 401, из 270 верных **0 получили 429** | достигнута |
| `generations` | 20 генераций, 2 воркера × 2 слота: 20 из 20 `done` за 117 с, позиции только убывали (наибольшая 16), p95 страниц 719 → 675 мс, **отношение 0,94** | достигнута |
| `kill-worker` | `kill -9` воркера с попыткой 1; уборщик вернул задание в очередь, второй воркер выполнил попытку 2, итог `done` через **142 с** | достигнута |
| `restart-web`, SIGKILL | соединение оборвано, **1 переподключение**, журнал полный (17 событий, как без рестарта), итог `done` | достигнута |
| `restart-web`, SIGTERM | соединение не оборвалось, переподключений 0, итог `done` | формально не достигнута, см. разбор |

Во время прогона в логах веба и воркеров не было ни одной ошибки. В `jobs` после прогона было 26 заданий, все `done`: 25 с первой попытки, 1 (из `kill-worker`) со второй.

### Разбор

**Страницы при 300 одновременных сессиях.** Каждый раунд — залп: 300 клиентов одновременно, и все запросы обслуживает один процесс Node. Задержка растёт примерно пропорционально числу одновременных запросов: при 100 сессиях p95 293 мс, при 300 — 713 мс. Ошибок нет ни в одном прогоне. Медленнее всего `/library` (серверный рендер): p95 1468 мс при 300 сессиях и 520 мс при 100. На ноутбуке генератор нагрузки и Postgres делят процессор с сервером, поэтому цифра для сервера отсюда не следует. Проверить на копии сервера. Если цель не будет достигнута и там, смотреть в первую очередь серверный рендер `/library` и пул базы (`max: 10` в `src/lib/db/client.ts`).

**Генерации не замедляют страницы.** Отношение p95 0,94, то есть на уровне шума: Chromium и пайплайн живут в процессах воркеров, веб только отдаёт SSE. Очередь вела себя как ожидалось. `/api/health` каждые 10 с показывал `running: 4` и убывающий `queued` (16 → 12 → 8 → 4 → 0). Воркеры взяли по 10 заданий. Одно задание шло в среднем 23 с, дольше всех в очереди ждали 94 с.

**kill -9 воркера.** Уборщик живого воркера записал в журнал `requeue`, и тот же воркер взял задание второй попыткой. Пользователь увидел предупреждение «Воркер перезапущен, генерация начата заново.». 142 с от старта — это аренда 60 с + запас 30 с + ожидание обхода уборщика (раз в 30 с) + сама генерация 23 с.

**Рестарт веба: мягкая остановка не рвёт SSE.** По SIGTERM `next start` сразу перестаёт слушать порт, поэтому новый веб поднимается без задержки. Уже открытые соединения старый процесс при этом обслуживает до конца: поток шёл дальше, задание завершилось, клиенту переподключаться было не нужно. Старый процесс завершился через 24 с, когда закрылся последний поток. Отдельная проверка с приостановленными воркерами (задание стоит в очереди, поток держится ping-ами): старый веб был жив и через 40 с после SIGTERM и завершился только после отключения клиента. Выводы:

- Проверка «SSE переподключается» имеет смысл только при оборванном соединении. Для неё нужна жёсткая остановка (`kill -9`), и с ней цель достигнута. В команде рестарта для копии сервера нужен `kill -9`, а не `kill`, иначе сценарий покажет «не достигнута» при исправной системе.
- **Риск для боевого сервера.** `systemctl restart showmehow` ждёт выхода старого процесса. Пока у кого-то открыта мастерская с идущей или ждущей генерацией, старый веб не выходит, а порт уже закрыт. Сайт будет недоступен до `TimeoutStopSec` службы (по умолчанию 90 с), после чего systemd пошлёт SIGKILL, и клиенты переподключатся. Устранить можно двумя способами: закрывать потоки заданий по SIGTERM (клиенты сами переподключатся к новому процессу) или задать небольшой `TimeoutStopSec` в `ops/systemd/showmehow-override.conf`. В этом цикле не сделано.

### Что осталось прогнать на копии сервера

Все пять сценариев в полном объёме, по задаче 16 плана `docs/superpowers/plans/2026-09-17-worker-queue-ops.md` (отдельный каталог и контейнер Postgres, веб на `127.0.0.1:3200`, два воркера по два слота, мок с задержкой 20 с), с записью разделов через `--out docs/ops/load-2026-09.md`:

1. `pages` — главный открытый вопрос: p95 < 500 мс при 300 сессиях на железе сервера.
2. `logins` — за настоящим `SHOWMEHOW_TRUST_PROXY=1`.
3. `generations` — память и процессор сервера при четырёх Chromium одновременно, влияние на боевой `/api/health`.
4. `kill-worker` — как в плане.
5. `restart-web` — с `--restart-cmd`, который **обрывает** соединения: `kill -9 $(sed -n 2p logs/pids); sleep 2; nohup node_modules/.bin/next start …`. В команде из задачи 16 стоит `kill`, его нужно заменить. Отдельно проверить, сколько длится `systemctl restart showmehow` при открытой мастерской (см. разбор).
