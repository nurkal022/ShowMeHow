# ShowMeHow — фундамент: аккаунты, база данных, квоты

**Дата:** 2026-09-06
**Статус:** утверждено, к реализации
**Основание:** ветка `agent-2.0-phase-a` завершена и отревьюена; продукт переходит из
однопользовательского прототипа в пробную версию с внешними тестерами

## 1. Цель и рамки

Сейчас ShowMeHow не знает, кто им пользуется. Симуляции лежат файлами в
`data/simulations/<uuid>/` без владельца, задания живут в `Map` в памяти процесса,
войти в приложение нельзя, потому что входить некуда. Это работает ровно для одного
человека на одной машине.

Пробная версия требует минимума, без которого нельзя пустить внутрь посторонних:
учётные записи, принадлежность данных, лимит на генерацию и защита сервера от того,
что десять человек нажмут «Создать» одновременно.

**Эта спецификация закрывает только фундамент.** Разговорный чат с историей,
организация библиотеки, пошаговый конструктор, дизайн-система и durable-очередь —
отдельные циклы, каждый со своей спецификацией. Здесь они упоминаются лишь там, где
фундамент обязан оставить для них место.

### Условия развёртывания

| Параметр | Решение |
|---|---|
| Размещение | VPS, `docker compose` (Next + Postgres на одном хосте) |
| Регистрация | открытая, любой заводит аккаунт сам |
| Библиотека | у каждого своя; чужие симуляции не видны |
| Вход | почта и пароль |
| Роли | `admin` (без лимита) и `user` (не более 10 генераций) |
| Ключ провайдера | общий, из переменных окружения; пользователи ключей не вводят |

## 2. Роли и доступ

Ролей ровно две. Админ назначается переменной окружения `SHOWMEHOW_ADMIN_EMAIL`:
аккаунт, зарегистрированный на эту почту, получает роль `admin`. Отдельного интерфейса
управления ролями нет — при необходимости роль правится в базе руками.

| | `user` | `admin` |
|---|---|---|
| Свои симуляции | полный доступ | полный доступ |
| Чужие симуляции | нет | нет |
| Лимит генераций | 10 за всё время | нет |

Админ намеренно **не** получает доступа к чужим библиотекам: это привилегия, которая в
пробной версии ничего не даёт, а разбирать её последствия для приватности придётся уже
сейчас. Разница между ролями исчерпывается квотой.

Неавторизованному доступны только `/login`, `/register`, `/api/auth/*` и статика.
Всё остальное, включая `/present/<id>`, требует сессии: публичных ссылок на симуляции в
этом цикле нет.

## 3. Схема данных

Postgres 16 в контейнере рядом с приложением. Клиент — `pg`, миграции — обычные SQL-файлы
в `migrations/`, применяемые скриптом `scripts/migrate.ts` (таблица `schema_migrations`
хранит применённые имена). ORM не вводится: запросов немного, а лишний слой абстракции
здесь дороже пользы.

```sql
CREATE TABLE users (
  id            uuid PRIMARY KEY,
  email         text NOT NULL UNIQUE,        -- нормализована: trim + lowercase
  password_hash text NOT NULL,               -- см. раздел 5
  role          text NOT NULL,               -- 'admin' | 'user'
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE sessions (
  token_hash text PRIMARY KEY,               -- sha256 от токена из cookie
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  expires_at timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE simulations (
  id         uuid PRIMARY KEY,
  owner_id   uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title      text NOT NULL,
  prompt     text NOT NULL,
  subject    text NOT NULL,
  tags       text[] NOT NULL DEFAULT '{}',
  warning    text,
  demo       text,                           -- slug вшитой демки или NULL
  created_at timestamptz NOT NULL,
  updated_at timestamptz NOT NULL
);
CREATE INDEX simulations_owner_updated ON simulations (owner_id, updated_at DESC);
CREATE UNIQUE INDEX simulations_owner_demo ON simulations (owner_id, demo)
  WHERE demo IS NOT NULL;                    -- идемпотентность установки примеров

CREATE TABLE jobs (
  id            uuid PRIMARY KEY,
  owner_id      uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  status        text NOT NULL,               -- 'queued'|'running'|'done'|'error'|'cancelled'
  request       jsonb NOT NULL,
  events        jsonb NOT NULL DEFAULT '[]',
  simulation_id uuid,
  error         text,
  created_at    timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX jobs_owner_status ON jobs (owner_id, status);
```

Таблицы `versions` здесь нет: история версий остаётся файлами в `history/`. Она появится
в цикле разговорного чата, когда версии начнут привязываться к сообщениям.

### Что остаётся файлами

`artifact.html`, `history/*.html` и `thumbnail.png` продолжают лежать в
`data/simulations/<id>/` на томе Docker. Артефакт — цельный файл, который отдаётся в
iframe и на экспорт как есть; класть его в базу незачем, а объектное хранилище — лишний
контейнер для пробной версии. Каталог по-прежнему адресуется по uuid симуляции, без
раскладки по владельцам: uuid не угадывается, а проверка владельца делается по базе до
любого обращения к диску.

## 4. Хранилище: репозиторий и два драйвера

[`src/lib/storage.ts`](../../../src/lib/storage.ts) — узкий модуль из десяти функций и
единственная точка, знающая, где лежат симуляции. Он и становится швом.

**Новый модуль `src/lib/db/repo.ts`** объявляет интерфейс метаданных:

```ts
export interface MetaRepo {
  insert(meta: SimulationMeta & { ownerId: string }): Promise<void>;
  get(id: string): Promise<(SimulationMeta & { ownerId: string }) | null>;
  listByOwner(ownerId: string): Promise<SimulationMeta[]>;
  touch(id: string): Promise<void>;
  remove(id: string): Promise<void>;
  findDemo(ownerId: string, slug: string): Promise<string | null>;
}
```

Два драйвера: `pgRepo` (боевой) и `memoryRepo` (тесты). Файловые операции остаются в
`storage.ts` и через репозиторий не проходят.

`storage.ts` сохраняет назначение, но каждая функция получает `ownerId` и **становится
асинхронной**. Это самая механическая и самая широкая правка цикла: девять потребителей
(`present/[id]/page.tsx`, шесть роутов `api/simulations/*`, `lib/demos.ts`,
`lib/pipeline/run.ts`) и четыре тестовых файла. Ни один из них не меняет логику — только
`await`.

Доступ проверяется **внутри** `storage.ts`: функция, получившая чужой `id`, возвращает
`null`, а не бросает исключение с намёком на существование записи. Роут превращает `null`
в 404 — не 403, чтобы по коду ответа нельзя было перебором узнать чужие id.

## 5. Аутентификация и сессии

Собственная реализация на `node:crypto`, без новых зависимостей и без Auth.js: нужен один
способ входа, а полный фреймворк аутентификации здесь дороже, чем полторы сотни строк,
которые он заменяет. Схема пользователей выбрана так, что добавить Google-вход позже
можно без миграции данных.

**Пароль.** `crypto.scryptSync(password, salt, 64)`, соль — 16 случайных байт. В базе
строка `scrypt$<salt hex>$<hash hex>`. Сравнение — `crypto.timingSafeEqual`. Требование к
паролю одно: не короче 8 символов.

**Сессия.** Токен — 32 случайных байта в base64url, в cookie `showmehow_session`
(`httpOnly`, `sameSite=lax`, `secure` при `NODE_ENV=production`, срок 30 дней). В базе
хранится только `sha256` от токена: утечка дампа базы не даёт войти. Срок продлевается
скользящим окном, но не чаще раза в сутки, чтобы не писать в базу на каждый запрос.
Просроченные строки удаляются лениво при обращении.

**Регистрация** (`POST /api/auth/register`): почта нормализуется и проверяется на формат,
дубликат → 409. Роль — `admin`, если почта совпадает с `SHOWMEHOW_ADMIN_EMAIL`, иначе
`user`. Сразу создаётся сессия: подтверждения почты в этом цикле нет.

**Вход** (`POST /api/auth/login`): при неверной почте и при неверном пароле — **один и тот
же** ответ 401 «Неверная почта или пароль», иначе форма входа превращается в способ
узнать, кто зарегистрирован. Не более 10 попыток с одного IP за 15 минут (счётчик в
памяти процесса; durable-хранилище лимитов — вопрос цикла эксплуатации).

**Выход** (`POST /api/auth/logout`): строка сессии удаляется, cookie гасится.

Восстановления пароля нет — почтового сервиса в контуре нет. Забывшему пароль его меняет
админ запросом к базе. Это осознанная плата за отсутствие зависимости от SMTP в пробной
версии.

### Проверка доступа

`middleware.ts` в Next.js работает в Edge-рантайме и **не может обращаться к Postgres**.
Поэтому обязанности разделены:

- **middleware** проверяет только наличие cookie и заворачивает страницы без неё на
  `/login?next=<путь>`, а запросы к `/api/*` — на 401. Это дешёвый фильтр, не гарантия.
- **`requireUser()`** в `src/lib/auth/session.ts` — настоящая проверка: читает токен,
  сверяет с базой, возвращает пользователя или бросает. Её вызывает **каждый** серверный
  компонент и каждый роут-хендлер под защитой. Ни один роут не полагается на middleware.

## 6. Квоты

Израсходованное считается запросом `COUNT(*) FROM jobs WHERE owner_id = $1 AND status =
'done'` — отдельный счётчик в `users` завёл бы вторую версию правды, которая рано или
поздно разойдётся с первой.

| Что | Тратит квоту |
|---|---|
| Успешно завершённая генерация | да |
| Отменённая или упавшая генерация | нет |
| Доводка существующей симуляции | нет |
| Установка 10 готовых примеров | нет |

Удаление симуляции квоту **не возвращает**: иначе лимит обходится циклом
«сгенерировал — скачал — удалил».

Исчерпанная квота: `POST /api/generate` отвечает 403 с текстом «Лимит пробной версии
исчерпан: использовано 10 из 10 генераций. Доработка уже созданных симуляций
по-прежнему доступна.» В интерфейсе под композером всегда видно «осталось N из 10»;
у админа этой строки нет.

## 7. Ограничители параллелизма

Одна генерация — это Chromium под Playwright, несколько минут работы и несколько запросов
к LLM. Десять одновременных положат VPS. Ограничителя два, оба в памяти процесса:

- **на пользователя — одна активная генерация.** Вторая попытка → 409 «У вас уже идёт
  генерация»;
- **на сервер — не более двух одновременно.** Сверх этого задание создаётся со статусом
  `queued` и ждёт своей очереди.

Статус `queued` — новый в `JobStatus`. Клиент получает по SSE событие
`{ type: 'queued', position: N }` и показывает «в очереди, перед вами N». Позиция
пересылается при каждом изменении очереди.

Ограничители живут в памяти и умирают вместе с процессом — как и сама очередь заданий.
Durable-очередь и переживание рестарта относятся к циклу эксплуатации; здесь достаточно
того, что после рестарта осиротевшее задание помечается ошибкой (это поведение уже есть).

## 8. Задания

`src/lib/jobs.ts` сохраняет форму (`Map` в памяти как источник для SSE), но:

- `Job` получает `ownerId`, а `JobStatus` — значение `queued`;
- персистентность переезжает из `data/jobs/*.json` в таблицу `jobs`;
- `getJob` доступен только владельцу; чужой id даёт 404;
- при старте процесса задания в статусах `running` и `queued`, найденные в базе,
  помечаются `error` с текстом «Сервер был перезапущен».

## 9. Миграция существующих данных

Скрипт `scripts/migrate-to-db.ts`, запускаемый один раз:

1. применяет миграции схемы;
2. создаёт администратора из `SHOWMEHOW_ADMIN_EMAIL` и `SHOWMEHOW_ADMIN_PASSWORD`
   (переменные читаются только этим скриптом);
3. переносит все `data/simulations/*/meta.json` в таблицу `simulations` с `owner_id`
   администратора; файлы остаются на месте и не копируются;
4. печатает, сколько записей перенесено и сколько пропущено как повреждённые.

Повторный запуск безопасен: перенос пропускает id, уже существующие в базе.
`data/jobs/*.json` не переносится — журнал завершённых заданий прототипа ценности не имеет.

Готовые демки после миграции принадлежат администратору. Новый пользователь видит пустую
библиотеку и кнопку «Установить 10 примеров», которая создаёт **его собственные** копии
из `demos/`; уникальный индекс `(owner_id, demo)` сохраняет идемпотентность установки.

## 10. Развёртывание

`docker-compose.yml` с двумя сервисами:

| Сервис | Образ | Назначение |
|---|---|---|
| `app` | на базе `mcr.microsoft.com/playwright` (Chromium уже внутри) | Next.js и пайплайн |
| `db` | `postgres:16-alpine` | база, том `pgdata` |

Том `data/` монтируется в `app` — там артефакты. Миграции применяются командой на старте
контейнера. Новые переменные окружения: `DATABASE_URL`, `SHOWMEHOW_ADMIN_EMAIL`,
`SHOWMEHOW_ADMIN_PASSWORD` (только для миграционного скрипта). Существующие переменные
провайдера не меняются.

## 11. Интерфейс

Минимум, необходимый фундаменту; полноценная дизайн-система — отдельный цикл.

- **`/login`** и **`/register`**: одна карточка по центру, два поля, кнопка, ссылка на
  соседнюю страницу, место под ошибку. Стилистика существующего тёмного интерфейса.
- **Шапка**: справа почта пользователя и «Выйти».
- **Композер**: под кнопкой «Создать» строка «осталось N из 10» (у админа отсутствует).
  При исчерпанной квоте кнопка недоступна, текст объясняет почему и напоминает, что
  доводка работает.
- **Очередь**: когда задание в статусе `queued`, вместо стадий показывается «в очереди,
  перед вами N».

## 12. Тестирование

- **Существующие тесты продолжают работать на `memoryRepo`** — они не замедляются и не
  требуют базы. Правка в них механическая: `ownerId` в вызовы и `await`.
- **Контрактный набор** (`tests/integration/repo-contract.test.ts`) гоняет один и тот же
  сценарий против обоих драйверов; для `pgRepo` нужен поднятый Postgres, и при его
  отсутствии набор пропускается с явным сообщением, а не падает.
- **Аутентификация** покрывается юнит-тестами: хеш и проверка пароля, срок и продление
  сессии, одинаковый ответ на неверную почту и неверный пароль, лимит попыток.
- **Изоляция владельцев** — отдельный тест на каждый защищённый роут: чужой id даёт 404.
- **Квота**: десятая генерация проходит, одиннадцатая отклоняется, отменённая не тратит,
  доводка не тратит, удаление не возвращает.
- **Ограничители**: вторая генерация того же пользователя даёт 409; третья на сервере
  становится `queued`.

## 14. Критерии приёмки

1. `docker compose up` поднимает приложение и базу; миграции применяются автоматически.
2. Незалогиненный посетитель с любого адреса, кроме `/login` и `/register`, попадает на
   `/login`; после входа его возвращает туда, куда он шёл.
3. Два пользователя, созданные подряд, не видят симуляций друг друга ни в библиотеке, ни
   по прямой ссылке `/?id=`, ни в `/present/<id>`, ни через `/api/simulations/<id>`.
4. Пользователь после десятой успешной генерации получает 403 с внятным текстом, но
   по-прежнему может дорабатывать существующие симуляции; у админа лимита нет.
5. Отменённая генерация квоту не расходует.
6. Вторая одновременная генерация того же пользователя отклоняется с 409; третья
   генерация на сервере встаёт в очередь и стартует сама, когда освобождается место.
7. `scripts/migrate-to-db.ts` переносит существующую библиотеку на администратора, и она
   открывается в интерфейсе без потерь; повторный запуск ничего не дублирует.
8. Новый пользователь ставит себе 10 примеров кнопкой в пустой библиотеке; повторное
   нажатие не создаёт дублей.
9. `npm test`, `npx tsc --noEmit` и `npm run build` зелёные.
