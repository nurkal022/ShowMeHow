# Цикл 1. Эксплуатация под нагрузку: воркер, очередь в базе, HTTPS, бэкапы

**Дата:** 2026-09-17
**Статус:** спецификация, ждёт утверждения владельцем
**Карта:** `docs/superpowers/2026-09-16-b2b-platform-roadmap.md`, цикл 1
**Опирается на:** `2026-07-13-jobs-and-progress-design.md`, `2026-09-06-accounts-foundation-design.md`

## 1. Цель и рамки

Генерация сейчас живёт внутри веб-процесса:

- задания, подписчики SSE и флаги отмены — карты в памяти (`src/lib/jobs.ts`);
- очередь и «одна генерация на человека» — тоже в памяти (`src/lib/limits.ts`);
- журнал событий пишется в базу только в конце;
- доработка симуляции идёт прямо в HTTP-запросе, в обход очереди, и тоже поднимает
  Chromium;
- рестарт процесса убивает все идущие генерации;
- второй экземпляр веба невозможен;
- в `next dev` генерация не работает: роуты получают разные экземпляры модуля с картой
  заданий. Из-за этого же красные e2e.

**Цель цикла:** генерация и доработка выполняются отдельным воркером, состояние
заданий целиком в Postgres, веб только принимает заявки и отдаёт прогресс. Плюс
базовая эксплуатация: HTTPS, бэкапы, проверка здоровья, нагрузочный прогон.

**Не входит:** автомасштабирование, Redis, объектное хранилище, несколько машин
(воркер и веб делят диск `data/`), метрики в Prometheus, экраны админки (цикл 6
читает данные, которые этот цикл начинает собирать).

**Новых зависимостей нет.** Очередь — на `pg`: `FOR UPDATE SKIP LOCKED` и
`LISTEN/NOTIFY`.

## 2. Архитектура

```
браузер ──POST /api/generate──▶ веб ──INSERT jobs (queued)──▶ Postgres
браузер ◀──SSE /stream──────── веб ◀──LISTEN job_events─────── Postgres
                                                                  ▲
                    воркер ──claim (SKIP LOCKED)──────────────────┤
                    воркер ──INSERT job_events + NOTIFY───────────┤
                    воркер ──heartbeat, продление аренды──────────┘
                    воркер ──artifact.html, thumbnail──▶ data/
```

- **Веб** не импортирует пайплайн и Playwright. Он создаёт задание, отменяет, читает
  события.
- **Воркер** — отдельный процесс `scripts/worker.ts`. Берёт задания, выполняет
  пайплайн, пишет события, сохраняет результат. Воркеров может быть несколько.
- **Postgres** — единственный источник правды о заданиях.

### Где работает воркер

| Окружение | Как |
|---|---|
| Боевой сервер | отдельная служба systemd `teseract-worker`, рядом с `showmehow` |
| Docker | отдельный сервис `worker` в `docker-compose.yml` из того же образа |
| `npm run dev` | встроенный воркер: `src/instrumentation.ts` запускает его один раз на процесс, если `SHOWMEHOW_EMBEDDED_WORKER=1` (в dev по умолчанию включён) |
| `npm test` | драйвер в памяти, см. раздел 9 |

Встроенный воркер в dev безопасен: состояние в базе, поэтому разные экземпляры модулей
роутов больше ничего не делят. Это закрывает известную слабость «генерация не работает
в dev» и чинит e2e.

## 3. Схема: миграция `005_job_queue.sql`

```sql
ALTER TABLE jobs ADD COLUMN kind text NOT NULL DEFAULT 'generate'
  CHECK (kind IN ('generate','refine'));
ALTER TABLE jobs ADD COLUMN priority int NOT NULL DEFAULT 0;
ALTER TABLE jobs ADD COLUMN target_simulation_id uuid;      -- для refine
ALTER TABLE jobs ADD COLUMN image_data_url text;            -- вход генерации; стирается по завершении
ALTER TABLE jobs ADD COLUMN locked_by text;
ALTER TABLE jobs ADD COLUMN locked_until timestamptz;
ALTER TABLE jobs ADD COLUMN attempts int NOT NULL DEFAULT 0;
ALTER TABLE jobs ADD COLUMN cancel_requested_at timestamptz;
ALTER TABLE jobs ADD COLUMN started_at timestamptz;
ALTER TABLE jobs ADD COLUMN finished_at timestamptz;

CREATE INDEX jobs_queue ON jobs (priority DESC, created_at) WHERE status = 'queued';
CREATE INDEX jobs_leases ON jobs (locked_until) WHERE status = 'running';

-- Одна активная генерация и одна активная доработка на человека — правилом базы,
-- а не резервацией в памяти.
CREATE UNIQUE INDEX jobs_one_active_generate ON jobs (owner_id)
  WHERE kind = 'generate' AND status IN ('queued','running');
CREATE UNIQUE INDEX jobs_one_active_refine ON jobs (owner_id)
  WHERE kind = 'refine' AND status IN ('queued','running');

CREATE TABLE job_events (
  job_id uuid NOT NULL REFERENCES jobs(id) ON DELETE CASCADE,
  seq    int  NOT NULL,
  event  jsonb NOT NULL,
  at     timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (job_id, seq)
);

CREATE TABLE workers (
  id         text PRIMARY KEY,           -- host:pid:случайный суффикс
  host       text NOT NULL,
  started_at timestamptz NOT NULL DEFAULT now(),
  seen_at    timestamptz NOT NULL DEFAULT now(),
  running    int NOT NULL DEFAULT 0
);

CREATE TABLE login_attempts (
  key text NOT NULL,
  at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX login_attempts_key_at ON login_attempts (key, at);
```

**Старые записи.** `jobs.events` остаётся и читается для заданий, у которых нет строк в
`job_events`. Новые задания пишут только в `job_events`.

**Квота** считает только `kind = 'generate' AND status = 'done'`. Без этой правки каждая
доработка начала бы тратить квоту.

## 4. Жизненный цикл задания

```
queued ──claim──▶ running ──done/error──▶ done | error
   │                 │
   │ cancel          │ cancel_requested_at → пайплайн бросает CancelledError
   ▼                 ▼
cancelled         cancelled
                     │
                     │ аренда истекла
                     ▼
           attempts < 2 ? queued : error
```

### Создание (веб)

`POST /api/generate`:
1. сессия, право на генерацию, провайдер настроен — как сейчас;
2. квота;
3. `INSERT INTO jobs (..., status 'queued', kind 'generate', priority, image_data_url)`.
   Нарушение `jobs_one_active_generate` — 409 «У вас уже идёт генерация»;
4. `NOTIFY job_queue`;
5. ответ `{ jobId }`.

Резервация в памяти (`reserveUser`) и гонка двух одновременных POST уходят: второй
INSERT упирается в уникальный индекс.

`POST /api/simulations/<id>/refine` становится таким же: проверяет владение и право,
создаёт задание `kind = 'refine'` с `target_simulation_id` и инструкцией в `request`,
отвечает `{ jobId }`. Квоту не тратит, как и раньше.

**Приоритет** считает чистая функция: платформенный админ, учитель и админ организации —
10, остальные — 0. Внутри приоритета — по времени создания.

### Захват (воркер)

```sql
UPDATE jobs SET status = 'running', locked_by = $1,
       locked_until = now() + interval '60 seconds',
       attempts = attempts + 1, started_at = coalesce(started_at, now())
WHERE id = (
  SELECT id FROM jobs WHERE status = 'queued'
  ORDER BY priority DESC, created_at
  FOR UPDATE SKIP LOCKED LIMIT 1
)
RETURNING *;
```

Воркер держит не больше `WORKER_CONCURRENCY` заданий (по умолчанию 2). Свободный слот
пробует захват сразу, по `NOTIFY job_queue` и раз в 5 секунд на случай потерянного
уведомления.

### Выполнение (воркер)

- Пайплайн вызывается как сейчас: `runPipeline` или `refineExisting` с `ctx.emit`.
- `emit` пишет событие в `job_events` со следующим `seq` и делает
  `NOTIFY job_events, '<jobId>'`. В полезной нагрузке уведомления только id:
  у NOTIFY предел 8000 байт, а события со скриншотами больше.
- Запись событий упорядочена цепочкой промисов, как в нынешнем `enqueueWrite`.
- **Сердцебиение** раз в 15 секунд одним запросом продлевает аренду всех своих
  заданий, возвращает их `cancel_requested_at` и обновляет строку `workers`.
  Флаг отмены кладётся в память воркера, `signal()` пайплайна читает его синхронно.
  Отмена срабатывает не позже чем через 15 секунд плюс время текущего шага.
- **Завершение** — одна транзакция: `status`, `simulation_id`, `error`, `finished_at`,
  `image_data_url = NULL`, `locked_by = NULL`, последнее событие.
- Событие `done` пишется только после успешной транзакции.

### Отмена (веб)

`POST /api/jobs/<id>/cancel`:
- `queued` — сразу `UPDATE ... SET status = 'cancelled' WHERE status = 'queued'` и
  событие `cancelled`;
- `running` — `cancel_requested_at = now()`; воркер завершит задание со статусом
  `cancelled`.

Повторный вызов безвреден.

### Потерянный воркер

Воркер убит, завис или машина перезагрузилась — аренда перестаёт продлеваться.
**Уборщик** запускается в каждом воркере раз в 30 секунд:

```sql
UPDATE jobs SET status = CASE WHEN attempts < 2 THEN 'queued' ELSE 'error' END, ...
WHERE status = 'running' AND locked_until < now() - interval '30 seconds'
```

- Возвращённое в очередь задание получает событие `warning` «Воркер перезапущен,
  генерация начата заново».
- Задание со второй потерей получает `error` «Генерация прервалась дважды. Попробуйте
  ещё раз».
- **Защита от двойного сохранения.** Воркер записывает `simulation_id` в задание сразу
  после `createSimulation`, до события `done`. Повторная попытка, увидев заполненный
  `simulation_id`, не генерирует заново, а только завершает задание как `done`.

### Мягкая остановка воркера

По `SIGTERM` воркер перестаёт брать новые задания, ждёт текущие до
`WORKER_DRAIN_SECONDS` (по умолчанию 600), затем выходит. Недоделанные подберёт
уборщик. Служба systemd: `TimeoutStopSec=660`. Выкладка веба воркер не трогает;
выкладка воркера не обрывает генерации, если они короче десяти минут.

## 5. Прогресс (веб)

`GET /api/jobs/<id>/stream`:

1. сессия, владение — как сейчас;
2. отдаёт все события из `job_events` по порядку (или `jobs.events` для старых);
3. подписывается на уведомления для этого задания и на каждое дочитывает события
   с `seq` больше последнего отданного;
4. пока задание в `queued`, раз в 3 секунды считает позицию и отправляет
   `{ type: 'queued', position }`, если она изменилась. Позиция в журнал не пишется;
5. закрывает поток на терминальном событии;
6. закрывает поток кадром-комментарием `: reconnect` через 5 минут жизни и по SIGTERM
   веб-процесса (реестр открытых потоков на процесс, обработчик ставит
   `instrumentation.ts`). `next start` по SIGTERM ждёт закрытия всех соединений, так что
   без этого рестарт веба висел бы, пока открыта хоть одна мастерская. Мастерская
   считает такое закрытие плановым: попытки не расходует и подключается снова через
   250–1000 мс. Служба `showmehow` получает `TimeoutStopSec=20` как страховку.

**Одно соединение на процесс.** `src/lib/jobs/listener.ts` держит один выделенный клиент
`pg` с `LISTEN job_events` и раздаёт уведомления подписчикам внутри процесса. Сорвалось
соединение — переподключается, и каждый подписчик дочитывает пропущенное по `seq`.
Независимо от уведомлений поток раз в 5 секунд сверяется с базой: потерянное
уведомление задерживает событие, но не теряет его.

Карта в памяти тут безопасна: это кэш соединения, а не источник правды. Два экземпляра
модуля в dev просто держат два соединения.

**Позиция в очереди:**

```sql
SELECT count(*) + 1 FROM jobs q, jobs me
WHERE me.id = $1 AND q.status = 'queued'
  AND (q.priority > me.priority
       OR (q.priority = me.priority AND q.created_at < me.created_at))
```

`GET /api/jobs/<id>` читает задание из базы. Логика «сервер был перезапущен» уходит:
её заменяет уборщик.

## 6. Интерфейс

- **Мастерская, генерация** — без изменений: тот же SSE, те же события.
- **Мастерская, доработка.** Сейчас `refine()` ждёт готовый HTML в ответе. Теперь
  получает `jobId` и слушает тот же поток. Пока задание идёт, показывается «Дорабатываю…»
  с кнопкой отмены. На `done` загружается свежий артефакт. Восстановление после
  перезагрузки страницы работает и для доработки: id активного задания хранится так же,
  как у генерации.
- **Очередь.** «В очереди, перед вами N» — как сейчас, но число честное для всех
  процессов.

## 7. Лимиты входа в базе

Счётчики из спецификации цикла 0 переезжают из памяти в `login_attempts`. Интерфейс
модуля `rate-limit.ts` тот же, но функции асинхронные. Порог проверяется запросом
`count(*) WHERE key = $1 AND at > now() - interval '15 minutes'`. Строки старше суток
удаляет уборщик воркера.

Счётчиков два, как в цикле 0: 10 неудач на идентификатор (на любую неудачу, есть такой
аккаунт или нет) и 300 неудач с одного IP. Ключи хранятся как sha256. Без базы
(разработка, юнит-тесты) счётчики живут в памяти процесса; в продакшне без
`DATABASE_URL` вход падает с ошибкой конфигурации.

`x-forwarded-for` доверяется только если запрос пришёл от прокси: переменная
`SHOWMEHOW_TRUST_PROXY=1` ставится там, где перед приложением стоит Caddy. Берётся
**последний** адрес заголовка — его дописал наш прокси, первые клиент подставляет сам.

**Без `SHOWMEHOW_TRUST_PROXY` адреса клиента нет, и счётчик IP отключён.** Адрес сокета
обработчики App Router в Next 15 не получают, а общий ключ на все запросы позволил бы
тремстам чужим ошибкам закрыть вход всему сайту. Счётчик идентификатора при этом
работает как обычно. Цена: пока прокси не настроен, тормоза на уровне IP нет — перебор
одного пароля по многим логинам ограничен только десятью попытками на каждый логин.

## 8. Эксплуатация

### HTTPS

Caddy на машине уже стоит. Добавляется **только** блок сайта Tesseract, прочие сайты
общей машины не трогаются:

```
<домен> {
  reverse_proxy 127.0.0.1:3100 {
    flush_interval -1          # SSE без буферизации
  }
}
```

Порт 3100 после этого слушает только `127.0.0.1`. `SHOWMEHOW_TRUST_PROXY=1`.
Cookie получает `Secure` автоматически: `isSecureRequest` уже смотрит на
`x-forwarded-proto`. После перехода на HTTPS кнопки VR появляются сами.

**Нужно от владельца:** домен и A-запись на 95.141.135.244.

### Бэкапы

`scripts/backup.sh`, запускается таймером systemd раз в сутки в 03:00:

1. `pg_dump` из контейнера `teseract-pg` в `~/teseract-backups/db/<дата>.sql.gz`;
2. `rsync --link-dest` каталога `data/` в `~/teseract-backups/data/<дата>/` —
   неизменённые файлы не копируются повторно;
3. удаляет копии старше 14 дней;
4. пишет итог в журнал; при ошибке — ненулевой код, systemd помечает запуск сбоем.

**Внешняя копия** — вопрос к владельцу: копия на той же машине не спасает от её потери.

**Проверка восстановления** — `docs/ops/restore.md`: поднять Postgres в контейнере,
залить дамп, указать `SHOWMEHOW_DATA_DIR` на копию, запустить приложение, войти,
открыть симуляцию. Процедура проходится один раз в рамках цикла, результат
фиксируется в документе.

### Здоровье

`GET /api/health` без входа отвечает:

```json
{ "db": "ok", "queued": 3, "oldestQueuedSec": 42, "running": 2,
  "workersAlive": 1, "lastWorkerSeenSec": 7 }
```

Код 503, если база недоступна или нет ни одного воркера, видевшегося за последнюю
минуту при непустой очереди. Персональных данных в ответе нет.

### Выкладка

Порядок из памяти проекта сохраняется (`fetch` → `merge --ff-only` → `migrate` →
`build` → рестарт) и дополняется рестартом `teseract-worker`. Первая выкладка цикла:
создать службу воркера и таймер бэкапа. Миграция `005` совместима с работающим старым
кодом, поэтому её можно накатить до рестарта.

`docs/ops/deploy.md` описывает службы, переменные и порядок.

## 10. Тестирование

**Юниты, без базы:**
- `policy.ts`: приоритет по ролям; решение уборщика по числу попыток;
- воркер на драйвере в памяти: захват не больше `WORKER_CONCURRENCY`; порядок по
  приоритету и времени; отмена ожидающего и идущего; мягкая остановка не берёт новых;
- повтор после потери: задание с заполненным `simulation_id` завершается без повторной
  генерации;
- поток прогресса: реплей плюс живые события без потерь и дублей; позиция в очереди
  меняется;
- существующие тесты роутов `generate`, `jobs`, `cancel` переходят на драйвер в памяти.

**Интеграционные, с `SHOWMEHOW_TEST_DATABASE_URL`:**
- два одновременных `claim` из разных соединений берут разные задания;
- второй `INSERT` активной генерации того же человека даёт 409, доработка при этом
  разрешена;
- истёкшая аренда возвращает задание в очередь, вторая потеря даёт `error`;
- `LISTEN/NOTIFY` доставляет события подписчику в другом соединении;
- квота не считает доработки;
- лимиты входа в базе дают те же ответы, что юниты цикла 0.

**e2e.** `npm run test:e2e` запускает `next dev` со встроенным воркером и мок-провайдером.
Цель — набор снова зелёный. Если красное останется по причинам вне цикла, оно
записывается в спецификацию с объяснением, а не замалчивается.

**Нагрузочный прогон** `scripts/load/run.ts` на копии сервера с мок-провайдером:

| Сценарий | Цель |
|---|---|
| 300 одновременных сессий открывают библиотеку и страницу симуляции | p95 < 500 мс |
| 300 входов за минуту с одного IP, 10 % с ошибкой | ни одного 429 для верных |
| 20 генераций одновременно при двух воркерах по 2 слота | все завершаются; позиции честные; p95 страниц не хуже прогона без генераций более чем вдвое |
| `kill -9` воркера посреди генерации | задание перезапущено и завершено вторым воркером |
| Рестарт веба посреди генерации | SSE переподключается, прогресс не теряется |

Результаты прогона записываются в `docs/ops/load-2026-09.md`.

## 11. Критерии приёмки

1. Генерация и доработка выполняются воркером; веб не загружает Playwright.
2. Рестарт веба посреди генерации не прерывает её; прогресс восстанавливается.
3. Убитый воркер не теряет задание: его подбирает другой или тот же после рестарта.
4. Два экземпляра веба на одной базе показывают одинаковый прогресс и одну очередь.
5. `npm run dev` генерирует; `npm run test:e2e` зелёный или его остаток объяснён.
6. Сайт открывается по HTTPS, порт 3100 снаружи закрыт, VR-кнопки появились.
7. Бэкап создаётся по таймеру; восстановление проверено и описано.
8. `/api/health` отражает очередь и живость воркеров.
9. Нагрузочный прогон выполнен, результаты записаны.
10. `npm test`, `npx tsc --noEmit` и `npm run build` зелёные.

## 12. Решения, которые стоит подтвердить

| Вопрос | Принято |
|---|---|
| Домен для HTTPS | нужен от владельца; без него пункт 6 приёмки не закрывается |
| Число воркеров на боевом | одна служба, 2 слота; второй слот памяти на машине под вопросом |
| Внешняя копия бэкапов | нужна площадка от владельца; пока только локальная |
| Повторов после потери воркера | одна попытка |
| Доработка через очередь | да; она больше не мгновенная, зато не душит сервер |

## 13. Известные отступления

- **Playwright в веб-процессе остался в двух местах:** восстановление версии
  (`POST /api/simulations/<id>/history` перерисовывает превью) и подстраховка при
  автоустановке встроенных примеров, когда у демки нет заранее снятого файла
  `thumbnail.png` (`ensureDemosForUser` → `installDemos`, вызывается из
  `GET /api/simulations`). Генерация и доработка из веба ушли полностью — критерий
  приёмки 1 выполняется для них; перенос этих двух путей в воркер — отдельная задача.
- **У уборщика потерянных заданий четыре исхода,** а не два: `queued` (первая потеря,
  `attempts < 2`), `error` (вторая потеря), `cancelled` (задание потеряно, но отмена
  уже была запрошена) и `done` (в задании уже записан `simulation_id` — симуляция
  создана, и готовый результат важнее опоздавшей отмены).
- **Сбой записи результата после успешной генерации.** Если запись `simulation_id`
  в задание (`markSaved`) не удалась уже после того, как симуляция создана в
  хранилище, задание завершается как `error` с сообщением «Не удалось записать
  результат генерации.», а сама симуляция остаётся в библиотеке осиротевшей — без
  связанного успешного задания. Происходит только при сбое записи в базу на этом
  шаге, поэтому считается редким.
- **Захват после потери аренды.** Воркер, чью аренду уборщик уже признал истёкшей,
  успевает сделать ещё один запрос на запись (примерно один круг до базы), прежде
  чем узнаёт об этом сам — тот же редкий класс дубликата или осиротевшей симуляции,
  что и в пункте выше.
- **Отмена не мгновенна.** Сердцебиение воркера продлевает аренду и проверяет флаг
  отмены раз в 15 секунд, поэтому отмена запущенного задания срабатывает между
  шагами пайплайна не позже чем через 15 секунд плюс время текущего шага. Доработка
  (`refine`) проверяет отмену только до и после вызова модели, а не между шагами
  внутри него.
- **Лимит входа без доверенного прокси.** Обработчики App Router в Next.js 15 не
  отдают адрес клиента, поэтому без `SHOWMEHOW_TRUST_PROXY=1` адреса клиента нет и
  счётчик по IP не ведётся вовсе — общего ключа на все входы тоже нет. Защиту
  аккаунтов по-прежнему даёт счётчик по идентификатору логина. Проверка и запись попытки к
  тому же не атомарны: параллельный всплеск запросов может превысить 10 попыток
  по одному идентификатору.
- **Ограничения длины.** Запрос на генерацию — не длиннее 20000 символов, инструкция
  доработки — не длиннее 4000, `imageDataUrl` (`data:image/...`) — не длиннее
  8 000 000 символов; при превышении роут отвечает 400.
- **Позиция в очереди не хранится.** События `{ type: 'queued', position }`
  пересчитываются и уходят в поток раз в 3 секунды, но в журнал `job_events` не
  пишутся: после переподключения позиция придёт заново, а не восстановится из
  истории.
- **Старые активные задания при выкладке.** Миграция `005_job_queue.sql` при накатке
  помечает все задания в статусах `queued` и `running` ошибкой «Сервер был
  перезапущен» — так прежде поступал код при чтении задания. Без этого шага
  уникальные индексы одной активной генерации и одной доработки на человека могли
  не создаться на уже существующих данных.
  Миграция не видит задания, которые прежний веб начал уже после неё — пока идёт
  `npm run build`. Такая строка остаётся `running` без аренды (`locked_until IS NULL`),
  и уборщик возвращает её в очередь, когда с `started_at` (или `created_at`) прошло
  больше 15 минут: прежний код вёл генерацию до 10 минут, и раньше этого срока вторая
  генерация могла бы пойти параллельно первой. До этого момента у человека висит
  «У вас уже идёт генерация». Картинка-образец такого задания не сохранялась, и повтор
  идёт без неё.
