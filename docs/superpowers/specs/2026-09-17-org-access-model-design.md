# Цикл 0. Модель доступа: организации, членства, вход по логину

**Дата:** 2026-09-17
**Статус:** спецификация, ждёт утверждения владельцем
**Карта:** `docs/superpowers/2026-09-16-b2b-platform-roadmap.md`, цикл 0
**Опирается на:** `2026-09-06-accounts-foundation-design.md` (аккаунты, сессии, квоты)

## 1. Цель и рамки

Сейчас в Tesseract есть только люди. Нет организаций, нет ролей внутри них, войти
можно только по почте. Этот цикл закладывает фундамент, на котором строятся кабинет
организации, курсы, задания и админка.

**Входит:**
- организации, членства с ролью, группы и учителя групп;
- вход по логину без почты;
- лимит неудачных входов, который не блокирует класс за одним школьным IP;
- короткие сессии для учеников;
- принудительная смена временного пароля;
- блокировка аккаунта;
- охранники доступа и разделы навигации по членствам;
- право на генерацию и квота с учётом членств;
- консольный скрипт управления организациями — до появления кабинета и админки.

**Не входит:** экраны кабинета организации (цикл 2), массовое создание учеников
(цикл 2), курсы (цикл 3), очередь в базе и лимиты в базе (цикл 1), админка (цикл 6).

**Инвариант цикла.** Пользователь без членств не замечает ни одного изменения.
Регистрация, вход по почте, мастерская, библиотека, лаборатории, профиль и квота
10 генераций работают как раньше.

## 2. Понятия

| Понятие | Что это |
|---|---|
| Платформенный админ | `users.role = 'admin'`, как сейчас. Ролей платформы по-прежнему две |
| Организация | школа, колледж или университет |
| Членство | человек в организации с одной ролью: `org_admin`, `teacher` или `student` |
| Группа | класс или поток внутри организации: «7А», «ИС-21» |
| Учитель группы | учитель, которому группа назначена; видит и ведёт её учеников |
| B2C-пользователь | человек без членств |

В одной организации у человека ровно одна роль; `org_admin` включает права учителя.
В разных организациях роли могут быть разными.

## 3. Схема: миграция `004_organizations.sql`

```sql
CREATE TABLE organizations (
  id          uuid PRIMARY KEY,
  slug        text NOT NULL UNIQUE,              -- латиница, цифры, дефис; 2–32 символа
  name        text NOT NULL,
  kind        text NOT NULL CHECK (kind IN ('school','college','university')),
  settings    jsonb NOT NULL DEFAULT '{}'::jsonb,
  archived_at timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE memberships (
  org_id     uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role       text NOT NULL CHECK (role IN ('org_admin','teacher','student')),
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)
);
CREATE INDEX memberships_user ON memberships (user_id);

CREATE TABLE groups (
  id          uuid PRIMARY KEY,
  org_id      uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  title       text NOT NULL,
  join_code   text UNIQUE,                       -- заполняется в цикле 2
  archived_at timestamptz,
  created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX groups_org ON groups (org_id);

CREATE TABLE group_members (
  group_id uuid NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
  user_id  uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  PRIMARY KEY (group_id, user_id)
);
CREATE INDEX group_members_user ON group_members (user_id);

CREATE TABLE group_teachers (
  group_id uuid NOT NULL REFERENCES groups(id) ON DELETE CASCADE,
  user_id  uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  PRIMARY KEY (group_id, user_id)
);

ALTER TABLE users ALTER COLUMN email DROP NOT NULL;
ALTER TABLE users ADD COLUMN login text UNIQUE;
ALTER TABLE users ADD CONSTRAINT users_has_identifier
  CHECK (email IS NOT NULL OR login IS NOT NULL);
ALTER TABLE users ADD COLUMN must_change_password boolean NOT NULL DEFAULT false;
ALTER TABLE users ADD COLUMN disabled_at timestamptz;

ALTER TABLE sessions ADD COLUMN sliding boolean NOT NULL DEFAULT true;
```

**Почему группа не проверяет организацию участника базой.** Ученик группы обязан
быть членом той же организации. Внешним ключом это не выражается без составных
ключей во всех таблицах; инвариант держит единственная функция добавления в группу
(раздел 7), и его проверяет тест.

**Настройки организации** (`organizations.settings`), белый список ключей по образцу
`sanitizePrefs`:

| Ключ | Тип | По умолчанию | Смысл |
|---|---|---|---|
| `studentsCanGenerate` | boolean | `false` | ученики этой организации могут генерировать |
| `studentLongSessions` | boolean | `false` | ученикам — обычные 30-дневные сессии |
| `teacherGenerationLimit` | number | `100` | лимит генераций учителя за всё время |

Неизвестные ключи отбрасываются при записи.

## 4. Идентификатор входа

Логин и почта различаются по символу `@`: у почты он есть всегда, у логина — никогда.

- **Логин**: `^[a-z0-9][a-z0-9._-]{2,39}$`, хранится в нижнем регистре.
  Формат, который генерирует цикл 2, — `фамилия.и.slug` транслитом, например
  `ivanov.i.sch12`. Здесь закрепляется только алфавит.
- **Поле входа** одно: «Почта или логин». Сервер нормализует ввод (trim + lowercase)
  и ищет по `email`, если есть `@`, иначе по `login`.
- **Регистрация** не меняется: только почта. Логин выдаётся организацией или скриптом.

Изменения в коде:

- `findUserByEmail` заменяется на `findUserByIdentifier(raw)`; `scripts/migrate-to-db.ts`
  и `scripts/seed-demos.ts` переходят на неё.
- `AuthUser` получает `email: string | null`, `login: string | null`,
  `displayName: string | null`, `mustChangePassword: boolean`.
- Функция `userLabel(u)` возвращает `displayName`, иначе почту, иначе логин; её
  показывает профиль, как и сейчас.
- Функция `userContact(u)` возвращает почту, иначе логин; её показывают шапка и меню
  аккаунта вместо `user.email`. У ученика почты нет, а у пользователя без членств меню
  остаётся прежним.
- Текст ошибки входа: «Неверный логин, почта или пароль.»
- В профиле строка под именем показывает почту или логин — что есть.

## 5. Лимит неудачных входов

Сейчас 10 неудач с одного IP за 15 минут закрывают вход всем с этого адреса. Школа
выходит в интернет через один адрес, и класс, вводящий новые пароли, заблокирует себя
за минуту.

Новые правила, хранилище пока в памяти (в базу переносит цикл 1):

| Счётчик | Когда растёт | Порог за 15 минут |
|---|---|---|
| по идентификатору | неверный пароль к существующему аккаунту | 10 |
| по IP, «неизвестные» | вход в несуществующий аккаунт | 50 |
| по IP, «все» | любая неудача | 300 |

Проверка до обращения к базе остаётся: если исчерпан счётчик идентификатора или любой
из счётчиков IP — 429. Ответ на неверный пароль и на несуществующий аккаунт по-прежнему
одинаковый, время ответа выровнено. Разделение счётчиков не даёт оракула: клиент
видит только одинаковые 401 и, возможно, 429.

**Что это даёт.** Класс из 30 учеников с опечатками набирает десятки неудач по
существующим аккаунтам — ниже порога 300. Перебор логинов упирается в порог 50.
Перебор пароля к одному ученику упирается в порог 10.

**Почему порог по IP блокирует и верные входы.** Соблазнительно пропускать верный
пароль даже при исчерпанном счётчике IP. Но тогда перебор одного частого пароля по
списку логинов продолжал бы находить совпадения: неудачи получали бы 429, а успехи —
200. Поэтому исчерпанный счётчик IP закрывает вход целиком, а пороги подняты так,
чтобы класс до них не доходил.

**Цена порога 50.** Ученики чаще ошибаются в логине, чем в пароле, а ошибка в логине
считается как вход в несуществующий аккаунт. Пятьдесят таких ошибок за 15 минут с
одного адреса — это уже не урок. Если пилот покажет обратное, порог поднимается
настройкой, а не переделкой.

## 6. Сессии, смена пароля, блокировка

### Короткие сессии учеников

Сессия короткая, если у человека есть членство `student` и нет ни одного членства
`teacher` или `org_admin`, и ни одна из его организаций не включила
`studentLongSessions`. Платформенный админ всегда получает обычную сессию.

| | Обычная | Короткая |
|---|---|---|
| Срок | 30 дней | 12 часов |
| Продление | скользящее, раз в сутки | нет (`sliding = false`) |
| Cookie `maxAge` | 30 дней | 12 часов |

Тип определяется при входе и дальше не пересчитывается. `setSessionCookie` получает
срок параметром.

### Временный пароль

`must_change_password = true` ставит тот, кто выдал пароль: скрипт этого цикла,
кабинет организации в цикле 2, админка в цикле 6.

- **API и страницы.** `currentUserFromRequest` и `currentUserFromCookies` для такого
  пользователя возвращают `null`, и роут
  отвечает 401 как обычно. Исключения читают пользователя через
  `currentUserAllowingPasswordChange`: `GET /api/me`, `POST /api/me/password`,
  `POST /api/auth/logout`. Новые роуты закрыты по умолчанию: защита не зависит от того,
  вспомнил ли автор о флаге.
- **Страницы.** Корневой layout читает пользователя разрешающим вариантом и вместо
  содержимого страницы показывает форму «Придумайте свой пароль» с двумя полями и
  кнопкой «Выйти». Путь страницы layout не нужен — подменяется любая страница.
  Страницы, которые при `null` уводят на `/login`, петли не создают: страница входа
  никуда не уводит, а layout подменит и её.
- **Смена.** При поднятом флаге текущий пароль не спрашивается: человек только что
  вошёл с временным, а школьник его уже не помнит. Флаг снимается, прочие сессии
  удаляются, как сейчас.
- Middleware не меняется.

### Блокировка

`disabled_at` не пустой — `resolveSession` возвращает `null`. Вход с верным паролем
отвечает 403 «Аккаунт заблокирован. Обратитесь к администратору организации.»;
с неверным — обычный 401. Сообщение о блокировке видит только тот, кто знает пароль.
Блокировка удаляет все сессии аккаунта. Данные не трогаются.

## 7. Доступ: модуль `src/lib/org/`

`src/lib/org/access.ts` — единственное место, которое знает, кто что может в
организации. Роуты вызывают его функции; при отказе роут отвечает 404.

```ts
export type OrgRole = 'org_admin' | 'teacher' | 'student';

export interface Membership {
  orgId: string; orgSlug: string; orgName: string;
  orgKind: 'school' | 'college' | 'university';
  role: OrgRole;
  settings: OrgSettings;
}

listMemberships(userId): Promise<Membership[]>          // архивные организации не входят
orgRoleOf(userId, orgId): Promise<OrgRole | null>
requireOrgRole(user, orgId, allowed: OrgRole[]): Promise<Membership | null>
                                                         // платформенный админ проходит всегда
canManageGroup(user, groupId): Promise<boolean>          // org_admin организации или учитель группы
isPlatformAdmin(user): boolean
```

`src/lib/org/groups.ts` — `addToGroup(groupId, userId)`: проверяет, что человек —
член организации группы, иначе бросает. Это единственный путь записи в `group_members`.

`src/lib/org/settings.ts` — `sanitizeOrgSettings`, `mergeOrgSettings`, значения по
умолчанию. Чистые функции без базы.

`src/lib/org/policy.ts` — чистые функции без базы, покрытые юнитами:

```ts
navSections(user: AuthUser, memberships: Membership[]): NavSection[]
canGenerate(user: AuthUser, memberships: Membership[]): boolean
sessionKind(user: AuthUser, memberships: Membership[]): 'long' | 'short'
generationLimit(user: AuthUser, memberships: Membership[]): number | null
```

### Право на генерацию

| Кто | Может генерировать |
|---|---|
| Платформенный админ | да |
| Без членств | да |
| Есть членство `teacher` или `org_admin` | да |
| Только `student` | да, если хотя бы одна организация включила `studentsCanGenerate` |

Отказ: `POST /api/generate` и `POST /api/simulations/<id>/refine` отвечают 403
«Генерация недоступна для учеников вашей организации.» Раздел «Создать» в навигации
для такого человека не показывается. Библиотека и лаборатории остаются.

### Квота

`quotaStatus` получает членства и берёт лимит из `generationLimit`:

| Кто | Лимит |
|---|---|
| Платформенный админ | без лимита |
| Учитель или админ организации | наибольший `teacherGenerationLimit` среди его организаций |
| Остальные | 10, как сейчас |

Подсчёт израсходованного не меняется. Текст об исчерпании берёт число из лимита, а не
из константы.

### Разделы навигации

Layout считает `navSections` на сервере и передаёт в `NavLinks` готовый список.
В этом цикле появляются только разделы, у которых есть страницы: «Создать»,
«Библиотека», «Лаборатории». Каждый следующий цикл добавляет свой раздел в
`navSections` вместе со страницей: «Курсы», «Преподавание», «Организация»,
«Прометей», «Админка». Так в навигации никогда не будет ссылки в пустоту.

## 8. Скрипт `scripts/org.ts`

До кабинета организации и админки организации ведутся из консоли. Скрипт работает
через те же функции `src/lib/org/*`, что потом будут звать экраны.

```bash
npm run org -- create --slug sch12 --name "Школа №12" --kind school
npm run org -- list
npm run org -- add-member --org sch12 --user teacher@example.com --role teacher
npm run org -- create-user --org sch12 --login ivanov.i.sch12 --name "Иванов Иван" --role student
npm run org -- create-group --org sch12 --title 7А
npm run org -- add-to-group --org sch12 --group 7А --user ivanov.i.sch12
npm run org -- assign-teacher --org sch12 --group 7А --user teacher@example.com
npm run org -- reset-password --user ivanov.i.sch12
npm run org -- disable --user ivanov.i.sch12
npm run org -- set --org sch12 studentsCanGenerate=true
```

`create-user` и `reset-password` печатают временный пароль один раз и ставят
`must_change_password`. Временный пароль — три слова из короткого словаря через дефис,
например `лиса-дом-семь`. Словарь без похожих на вид слов, длина пароля не меньше
восьми символов. Генератор — чистая функция на `crypto.randomInt`.

README получает раздел «Организации» с этими командами. SQL-рецепт сброса пароля
заменяется на `reset-password`.

## 9. Ошибки и крайние случаи

| Случай | Поведение |
|---|---|
| Логин с `@` в скрипте | отказ с текстом про допустимые символы |
| Слаг занят | отказ, ничего не создано |
| Добавление в группу человека не из организации | отказ, `group_members` не тронута |
| Организация в архиве | её членства не учитываются ни в навигации, ни в правах, ни в квоте |
| Человек в двух организациях с разными `studentsCanGenerate` | разрешает любая |
| Учитель потерял членство | его сессии продолжают жить, права пересчитываются на следующем запросе |
| Старый пользователь без логина | входит почтой, как раньше |
| Почта совпадает с `SHOWMEHOW_ADMIN_EMAIL` | роль `admin`, как раньше |

## 10. Тестирование

**Юниты, без базы:**
- `policy.ts`: все строки таблиц права на генерацию, квоты, типа сессии и разделов;
- `settings.ts`: белый список, значения по умолчанию, слияние;
- генератор временного пароля: формат, длина, словарь;
- разбор идентификатора: почта против логина, нормализация, недопустимые логины;
- лимит входа: 30 неудач по разным существующим аккаунтам с одного IP не дают 429;
  51-я неудача по несуществующим даёт 429; 11-я по одному аккаунту даёт 429;
- `userLabel`.

**Интеграционные, с `SHOWMEHOW_TEST_DATABASE_URL`:**
- миграция накатывается на базу с данными прежней схемы; старые пользователи входят;
- вход по логину и по почте; одинаковый 401 на неверный логин и неверный пароль;
- короткая сессия ученика: срок 12 часов, не продлевается; у учителя — 30 дней;
- временный пароль: `/api/simulations` отвечает 401, `/api/me` — 200 с флагом;
  смена без текущего пароля снимает флаг; после смены `/api/simulations` отвечает 200;
- блокировка: сессии удалены, вход с верным паролем — 403, с неверным — 401;
- изоляция: `requireOrgRole` для чужой организации — `null`; платформенный админ проходит;
- `addToGroup` отказывает человеку из другой организации;
- генерация: ученик без разрешения получает 403, с разрешением — проходит; учитель
  получает лимит организации;
- архивная организация не даёт прав.

**Регрессия:** весь существующий набор проходит без смысловых правок. Меняются только
вызовы `findUserByEmail` и ожидания текста ошибки входа.

## 11. Критерии приёмки

1. Миграция накатывается на боевую базу без потерь; все прежние аккаунты входят.
2. Пользователь без членств не видит изменений в интерфейсе.
3. Скрипт создаёт организацию, группу, учителя и ученика с логином; ученик входит по
   логину, видит форму смены пароля и после смены попадает в приложение без раздела
   «Создать».
4. Тридцать неудачных входов по разным аккаунтам с одного IP не блокируют тридцать
   первый верный вход.
5. Сессия ученика истекает через 12 часов.
6. Заблокированный пользователь выброшен из всех сессий и не может войти.
7. `npm test`, `npx tsc --noEmit` и `npm run build` зелёные.

## 12. Решения, которые стоит подтвердить

| Вопрос | Принято |
|---|---|
| Срок короткой сессии | 12 часов, без продления |
| Лимит генераций учителя | 100 за всё время, меняется настройкой организации |
| Формат логина | `фамилия.и.slug` транслитом |
| Пароль-трёхсловие по-русски | да; на клавиатуре без русской раскладки неудобен — тогда латинский словарь |
| Текущий пароль при принудительной смене | не спрашивается |
