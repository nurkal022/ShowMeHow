# Движок тренажёров v2: сложнее, стабильнее, удобнее в доработке

Дата: 23.09.2026. Ветка-основа: `ui-refresh`.

## 1. Почему сейчас получается «суперпросто»

Разбор текущего кода (`src/lib/pipeline/*`, `src/lib/roles.ts`, `src/lib/runtime/doc.ts`):

| # | Причина | Где |
|---|---------|-----|
| 1 | **Весь тренажёр пишется одним ответом модели** с потолком 16k токенов. Одобренные демки весят 11–26 КБ (~4–8k токенов), значит сложнее них физически не влезает: модель заранее «экономит» и упрощает. | `roles.ts` `HTML_MAX_TOKENS`, `stages.ts` `generateCandidate` |
| 2 | **Планировщик просит 2–4 параметра и одну сцену.** В спецификации нет объектов, нескольких видов, сценария урока, заданий, измерений — только строки `physics` и `visualPlan`. Нечего усложнять, если план простой. | `prompts.ts` `PLANNER_SYSTEM` |
| 3 | **Каркас-образец — падающий мячик**, эталон — целый чужой файл. Оба тянут к уровню «сцена + слайдер + график». | `EXAMPLE_SKELETON`, `exemplars.ts` |
| 4 | **Проверки меряют исправность, а не глубину.** Пробы ловят «пауза не работает», критик — видимые косяки на скриншотах. Никто не проверяет, что все цели обучения реально показаны и что физика верна численно. Фиксер при этом правит «минимально» — ещё один сдвиг к простоте. | `probes.ts`, `CRITIC_SYSTEM` |
| 5 | **Спецификация не сохраняется.** После генерации она теряется, доработка видит только HTML и просьбу — не знает целей, физики, параметров. | `runPipeline` → `createSimulation` |
| 6 | **Доработка ограничена точечными правками по 1–15 строк** (обычно 1–6 штук). Структурные просьбы («добавь второй вид», «сделай режим заданий») не ложатся и уходят в полное переписывание, которое упирается в тот же потолок токенов и чаще всё ломает. | `edits.ts`, `REFINER_EDITS_SYSTEM` |
| 7 | **После доработки проверка слабее, чем после генерации**: только запуск и починка ошибок, без проб, критика и сравнения «стало лучше или хуже». Можно незаметно откатить качество. | `refineExisting` |
| 8 | **Уточняющий вопрос есть только у доработки.** При генерации модель сама решает уровень сложности, аудиторию и что показывать. | `clarify.ts` |
| 9 | **Нет замеров.** Нет набора эталонных запросов и истории оценок, поэтому любое изменение промпта — на глаз. «Стандарт» идёт ~11 минут, и непонятно, где именно время. | — |

Вывод: одним промптом это не лечится. Нужны (а) богатый план, (б) генерация по частям, (в) проверки, которые меряют глубину и точность, (г) доработка, которая понимает устройство тренажёра.

## 2. Целевая схема

```
Бриф ──► План v2 ──► [утверждение плана человеком] ──► Ядро физики ──► Каркас ──► Слои ──► Проверка ──► Критики ──► Сохранение
 (вопросы)  (JSON)         (редактируемая карточка)      (тестируется   (сцена,   (приборы,  (пробы +    (физик,
                                                          отдельно)     панель)   виды,      инварианты) методист,
                                                                                  задания)               «ученик»)
```

Главная идея: **тренажёр — это не один файл, а набор секций**, и каждая секция создаётся, проверяется и правится отдельно.

### Секционированный артефакт

HTML по-прежнему один файл (кит, экспорт, LMS не меняются), но код внутри размечен:

```js
// @section config      — SIM_CONFIG: параметры, пресеты, цвета, подписи (JSON)
// @section physics     — чистые функции: init(params), step(state, params, dt), observables(state)
// @section scene       — отрисовка
// @section instruments — SimUI: показания, графики, формулы, баннер
// @section scenario    — режимы урока, задания, подсказки
// @section main        — цикл, expose, resize
```

Это даёт:
- генерацию по частям без потолка в 16k токенов на весь файл;
- починку и доработку одной секции целиком вместо хрупких find/replace;
- правку параметров, подписей и цветов **без модели** — через `SIM_CONFIG`;
- возможность отдельно прогнать физику в Node и проверить её числами.

Спецификация (`spec.json`) и карта секций сохраняются рядом с артефактом и версионируются вместе с ним.

## 3. План по этапам

Порядок выбран так: сначала замеры (иначе улучшения не доказать), потом фундамент (план и секции), потом всё, что на нём строится. Каждый этап даёт видимый результат сам по себе.

### Этап 0. Замеры и эталонный набор (1–2 дня)

Без этого непонятно, стало ли лучше.

1. **Набор из ~20 эталонных запросов** `eval/prompts.json`: разные предметы (физика, химия, биология, техника), 2D/3D, простые и заведомо сложные («четырёхтактный двигатель с p-V диаграммой», «электрическая цепь с переключаемыми элементами», «эволюция популяции хищник-жертва», «интерференция от двух щелей с изменяемой геометрией»).
2. **Скрипт `scripts/eval.ts`**: гонит набор через `runPipeline` без базы (Ctx без `draft`), сохраняет HTML, спецификацию, отчёт проб, оценки судьи, время и токены по каждой роли в `eval/runs/<дата>/`.
3. **Метрики сложности**, считаются автоматически: число параметров, приборов, графиков, видов, режимов/заданий, объём кода физики, доля пройденных проб, оценки судьи, время, стоимость.
4. **Хронометраж по этапам**: события `stage` и `usage` уже есть — пишем их в задание и показываем в админке сводку «где уходят минуты» (разобраться, откуда 11 минут у «стандарта»).
5. **`pipelineVersion` в meta** каждой симуляции — чтобы сравнивать поколения движка.

Критерий готовности: одна команда выдаёт таблицу «запрос × метрики», есть базовый прогон текущего движка.

### Этап 1. План v2 и утверждение плана (3–4 дня)

1. **Новая схема `PlanSpec`** (обратно совместимая: старые поля остаются):
   - `level`: `demo` | `lab` | `research` — демонстрация / интерактивная лаборатория / исследование с заданиями;
   - `audience`: школа (класс) / колледж / вуз;
   - `entities[]`: объекты сцены с их свойствами и связями (поршень, клапан, газ; или хищники, жертвы, среда);
   - `parameters[]`: до 8, с группировкой (`group`), не 2–4;
   - `observables[]`: что измеряется и выводится (имя, единицы, формула);
   - `views[]`: основная сцена + дополнительные виды (график, фазовая диаграмма, разрез, вид сверху, таблица);
   - `invariants[]`: проверяемые утверждения о физике («полная энергия сохраняется при трении 0 с точностью 1%», «период не зависит от массы», «при T→2T давление ×2»);
   - `scenario[]`: шаги урока / режимы (наблюдай → измени → предскажи → проверь), для `lab` и `research` — задания с проверкой ответа;
   - `wowMoment`: ради чего тренажёр показывают;
   - `presets[]`: осмысленные режимы.
2. **Планировщик считает объём под уровень**: `demo` — 2–4 параметра, 1 вид; `lab` — 4–6 параметров, 2–3 вида, измерения; `research` — сценарий с заданиями, сравнение режимов.
3. **Проверка и нормализация спецификации** кодом (`lib/pipeline/spec.ts`): обязательные поля, диапазоны `min < value < max`, уникальные `name`, единицы; мелкие ошибки чиним сами, крупные — один повторный запрос планировщику с перечнем.
4. **Уточнение до генерации**: тот же механизм, что в `clarify.ts`, но для брифа — спрашивать уровень, аудиторию и главный акцент, только если из запроса не ясно. Кнопки-варианты + поле «своё» (правило «подсказка не рамка»).
5. **Карточка плана с утверждением** (для «стандарта» и «максимума», в «быстро» — пропускается):
   - после этапа планирования задание встаёт на паузу `awaiting-plan`;
   - в Workbench показывается карточка: название, цели, параметры (редактируемые диапазоны), виды, сценарий, «вау-момент»;
   - человек правит поля или пишет «добавь ещё …» (перепланирование — секунды, а не минуты генерации);
   - «Генерировать» продолжает задание. Таймаут ожидания — продолжаем как есть.
   - Это самое дешёвое место исправить «слишком просто»: до того, как потрачены минуты.
6. **`spec.json` сохраняется** рядом с симуляцией и в каждой версии истории.

### Этап 2. Генерация по частям (5–7 дней) — ядро улучшения

1. **Ядро физики отдельно** (`stage: physics`):
   - модель пишет только секцию `physics`: `init`, `step`, `observables` — чистый JS без DOM;
   - прогоняем в Node (`vm` с таймаутом): шаги без исключений и NaN, наблюдаемые в разумных пределах, **проверка `invariants`** из плана численно (энергия, пропорциональности, предельные случаи);
   - провал → один-два круга починки только этой секции с конкретными числами («энергия выросла на 34% за 10 с при трении 0»).
   - Это главный шаг к точности: сейчас физика проверяется только по скриншотам.
2. **Каркас** (`stage: scaffold`): `config` + `scene` + `main` на готовом ядре. Результат — первый рабочий черновик, его сразу видно в превью (механизм `draft` уже есть).
3. **Слои** (`stage: layers`): по плану добавляются `instruments`, дополнительные `views`, `scenario`. Каждый слой:
   - генерируется как замена/добавление своей секции (ответ маленький, быстрый);
   - проверяется рендером и пробами;
   - при поломке — откат слоя и одна попытка заново; второй провал — слой пропускается с предупреждением, тренажёр не теряется.
   Число слоёв зависит от `level` — так и появляется «более сложная структура», не упираясь в лимит ответа.
4. **Сборщик секций** (`lib/pipeline/sections.ts`): разбор маркеров, замена секции, проверка, что все обязательные секции на месте; старые артефакты без маркеров работают по старому пути.
5. **Новый каркас-образец и эталоны по секциям**: вместо мячика — каркас с секциями; из эталона в промпт идёт только нужная секция нужного уровня (например, `instruments` из engine), а не весь чужой файл — меньше токенов и меньше копирования темы.
6. **Параллельность**: сцена и приборы зависят от ядра, но не друг от друга — после ядра их можно генерировать параллельно и собирать.

### Этап 3. Проверки глубины и точности (3–4 дня)

1. **Новые пробы** (`probes.ts`):
   - **чувствительность каждого параметра**: движение слайдера меняет хотя бы одну наблюдаемую из `observables` (сейчас проверяется только «что-то изменилось»);
   - **инварианты в браузере**: те же проверки, что в ядре, но на живом `getState()`;
   - **пресеты**: каждый пресет приводит к заметно другому состоянию;
   - **узкий экран**: рендер в 390×844, сцена не перекрыта панелями;
   - **производительность**: FPS не ниже порога, нет утечки по памяти за 20 с;
   - **сценарий**: шаги/задания переключаются, проверка ответа реагирует.
2. **Покрытие плана**: автоматическая сверка «что в плане ↔ что в артефакте» — все параметры, виды, наблюдаемые и шаги сценария присутствуют. Недостающее идёт в слой-добор, а не теряется.
3. **Критик v2 — три взгляда** (vision, параллельно):
   - физик — корректность (как сейчас);
   - методист — видна ли каждая цель из `learningGoals`, понятен ли сценарий, есть ли «вау-момент»;
   - «ученик» — понятно ли, что делать, в первые 10 секунд.
   Замечания привязываются к секциям, чтобы целевая починка шла по нужной секции.
4. **Судья с порогом глубины**: к рубрике добавить `depth` (насколько тренажёр соответствует заявленному `level`). В «максимуме» доводка идёт, пока `depth` ниже порога.
5. **Классификатор ошибок консоли** → подсказки фиксеру («THREE is not defined» → «используй import из importmap», «Cannot read properties of undefined (reading 'push')» → «прибор создан после первого вызова») — меньше слепых кругов.

### Этап 4. Доработка v2 (4–5 дней)

1. **Доработка знает спецификацию и секции**: в промпт уходит `spec.json`, карта секций и только нужные секции целиком, а не весь файл.
2. **Маршрутизатор просьбы** (дешёвая модель, тот же вызов, что уточнение):
   - `config` — поменять диапазон, подпись, цвет, пресет → **правка без генерации кода**, секунды;
   - `tweak` — точечные find/replace (как сейчас);
   - `section` — переписать 1–2 секции целиком;
   - `structural` — изменение плана («добавь второй вид», «сделай режим заданий») → дельта спецификации → новые/переписанные секции через тот же механизм слоёв.
   Уточняющий вопрос остаётся, но задаётся тем же вызовом.
3. **Полная проверка после доработки**: рендер + пробы + покрытие плана; критик — в фоне. **Защита от регрессии**: если доля проб или покрытие упали, правка не применяется молча — показываем «стало хуже: пауза сломалась; применить всё равно / откатить / попробовать ещё».
4. **Правка параметров руками**: панель «Настройки тренажёра» в Workbench из `SIM_CONFIG` — диапазоны, значения по умолчанию, подписи, единицы, пресеты, цвета. Сохранение — новая версия без вызова модели.
5. **Очередь просьб**: несколько просьб подряд встают в очередь одного задания, выполняются по очереди, каждая — отдельной версией.
6. **Отчёт → действия**: пункты `next` из отчёта модели и мелкие замечания критиков превращаются в кнопки «Улучшить: …» под превью.

### Этап 5. UX работы над тренажёром (5–7 дней)

Набор, который делает процесс «как в редакторе», а не «чат и ждём».

1. **Прогресс как сборка**: вместо таймлайна этапов — схема секций тренажёра, которые загораются по мере готовности (ядро ✓ → сцена ✓ → приборы ✓ …) с анимацией; превью обновляется черновиками на каждом шаге. Честная оценка времени по истории замеров из этапа 0.
2. **«Покажи и скажи»**: в режиме выбора человек кликает в превью (элемент сцены или виджет кита) или обводит область → в просьбу уходят координаты, скриншот фрагмента и ближайший виджет/секция. «Сделай вот это крупнее» работает без описаний.
3. **Панель качества**: чек-лист проб, инвариантов и покрытия плана с зелёными/красными пунктами; у красного — кнопка «Починить».
4. **Версии по-человечески**: лента версий с миниатюрами и одной строкой «что изменилось» (из отчёта); сравнение двух версий бок о бок в двух превью; откат одной кнопкой; «ветка» — попробовать вариант, не теряя основной.
5. **Карточка плана** (этап 1) как постоянная вкладка «План» — её можно править и после генерации, изменения идут структурной доработкой.
6. **Горячие шаблоны просьб** по контексту: «добавить задание», «добавить график величины …», «упростить для 7 класса», «перевести на казахский/английский», «сделать режим сравнения».
7. **Режим «проверь как ученик»**: превью без панели учителя, с таймером — посмотреть глазами студента перед публикацией в курс.
8. **Оценка результата**: 👍/👎 и «сделать эталоном» — лучшие тренажёры организации попадают в библиотеку эталонов (этап 6).

### Этап 6. Расширение кита и эталонов (4–6 дней, можно параллельно с этапом 4–5)

Чем больше готовых примитивов, тем меньше кода пишет модель и тем сложнее может быть тренажёр при том же объёме ответа.

1. **Новые виджеты `SimUI`**: таблица измерений (с записью точек по кнопке), линейка/транспортир-измеритель на сцене, шкала времени с перемоткой и пошаговым режимом, карточка задания (вопрос → ответ → проверка → подсказка), вкладки видов, сравнение двух режимов в сплит-экране.
2. **`SimPhys` — физические помощники**: интеграторы (Эйлер-Кромер, RK4, Верле), столкновения частиц, поля, пружины/связи, система частиц. Модель вызывает, а не пишет заново — меньше ошибок физики.
3. **3D-помощники** поверх three.js: камера по размеру объекта, стандартный свет, подписи в 3D.
4. **Обновить конструктор-стенд**: он обещает ровно то, что умеет кит, — новые приборы должны появиться и там, иначе расхождение.
5. **Эталоны**: разметить 10 демок секциями; добавить механизм «одобренный тренажёр организации → эталон»; подбор эталона по близости спецификации и уровню.

### Этап 7. Скорость и стабильность движка (2–3 дня, после замеров)

1. **Кэш промпт-префикса**: правила, документация кита, каркас — неизменный префикс системного сообщения; если провайдер поддерживает кэш — включить (снижение цены и времени на каждом вызове).
2. **Модели по ролям**: маршрутизатор, уточнение, нормализация — дешёвая быстрая модель; ядро физики и слои — сильная; фиксер секций — средняя. Настройки ролей уже есть (`roles.ts`) — задать умолчания.
3. **Бюджеты**: у каждого этапа и режима — лимит времени и кругов; при исчерпании — сохраняем лучшее, что есть, с предупреждением, а не висим.
4. **JSON-ответы**: где провайдер умеет `response_format: json_object` — включить для планировщика, критиков, правок; остальное — через существующий терпимый разбор.
5. **Повторное использование рендера**: один запуск Chromium на задание вместо запуска на каждую проверку (если сейчас не так — проверить по замерам).
6. **Возобновление с этапа**: промежуточные результаты (spec, ядро, секции) пишутся в задание — воркер после падения продолжает с последнего этапа, а не с нуля.

После каждого этапа — прогон эталонного набора и сравнение с базой.

## 5. Критерии успеха

- На эталонном наборе уровень `lab`: в среднем ≥5 параметров, ≥2 вида, ≥3 наблюдаемых, есть сценарий; сейчас — 2–4 параметра и один вид.
- ≥90% инвариантов из плана проходят численную проверку.
- Доля тренажёров, сохранённых «с ошибками», — меньше 5%.
- Доработка: ≥85% просьб применяются с первого раза без регрессии проб; правки `config` — меньше 3 секунд.
- «Стандарт» укладывается в честно показанное время (цель — ≤5 минут для `lab`).

## 6. Риски

- **Секции ломают старые артефакты** → маркеры необязательны, без них — старый путь; миграции файлов нет.
- **Слои раздувают время** → слои строго по `level`, бюджет времени на режим, параллельная генерация сцены и приборов.
- **Утверждение плана раздражает** → только в «стандарте»/«максимуме», отключается в настройках, по таймауту продолжаем сами.
- **Проверка физики в Node — исполнение чужого кода** → `vm` в воркере с таймаутом и без доступа к `require`/сети; воркер уже изолирован от веба.
- **Больше вызовов — дороже** → дешёвые модели на служебные роли, кэш префикса, меньшие ответы (секции вместо файла).

## 7. С чего начать

Этап 0 и сохранение `spec.json` (пункт 1.6) — они нужны всем остальным этапам и ничего не ломают. Следом — схема плана v2 и карточка утверждения: дешевле всего и сразу даёт тренажёры сложнее.
